# 同伴可否判定の正解セット

`pet-policy-gold.json` — 東京都心部40件を、公式サイト・掲載系サイト（ぐるなび／ホットペッパー／
一休等）・Google口コミから独立に調べた結果。2026-08-18 作成。各件に根拠URLか原文引用が入っている。

## 何のためにあるか

検証パイプラインには合否判定が無く、実行しても精度が測られない。だから何度回しても
同じ誤りを繰り返し、失敗が失敗として記録されない。作成時点の実測は次のとおり。

| | |
|---|---|
| 全体（判定可能32件） | 65.6% |
| 飲食店・公園・ホテルのみ | **56.0%** |
| 現地で断られうる件 | 17.5% |

全体65.6%は水増し。一致21件のうち7件は動物病院・ドッグランで、カテゴリだけで自明に
allowed になる施設。精度を報告するときは必ずカテゴリ別に分けること。

## 使い方

パイプラインを変更したら、**本番へ流す前にこの40件だけで走らせて精度を測る**。
基準を満たしてから初めて全件に金を使う。測るのは `wanspot/scripts/eval-pet-policy.ts`。

```
npx tsx --env-file=.env.local scripts/eval-pet-policy.ts \
  --gold=../wanspot-native/eval/pet-policy-gold.json \
  --out=../wanspot-native/eval/pet-policy-baseline.json
```

`persistVerificationOutcome` を通さない dry-run なので `pet_friendly_*` は書き換わらないが、
**Anthropic / Brave・CSE / Places の課金は実際に発生する**。40件で $3.4〜4.4。
支出は `PET_VERIFY_COST_LABEL='pet-verify-eval'` で分計する。

注意が3つある。どれも実際に踏んだ。

- `pet-verify-eval` は `SEPARATE_BUDGET_OPERATIONS` に入っていないので**日次の自動化上限に載る**。
  上限に触れると `pauseAllPaidAutomation` が収集・検証・記事生成を止める。測る日は残高を見ること
- `SpendBudget` の判定は「その日のラベル合計」なので、同じ日に2本目を回すと最初から残高が
  減った状態で走り、途中で打ち切られる。打ち切られたら `--resume=<前回のjson>` で続きから
- タイムアウトを短くすると、測っているのが精度ではなくタイムアウト設定になる。
  30秒だと全件が、90秒・並列3でも40件中9件が `llm_unreachable` の unknown で確定した。
  既定（120秒・並列2・届かなければ1回引き直す）を下げないこと

## 精度の数え方

- `truth = undeterminable`（8件）は分母から外す。情報が世に存在しない群で、
  ここを埋めさせると精度が実態より良く出る
- `confidence = low`（9件）も分母から外す
- **カテゴリ別に出す。** 動物病院・ドッグランは自明なので、飲食店・公園の数字を主指標にする
- **誤りの向きを分ける。** DBが実際より緩い（現地で断られる）誤りは、厳しすぎる誤りより
  コストが高い。同じ1件として数えない

## 出荷基準（案）

飲食店・公園カテゴリで、
- 現地で断られうる誤り（db_too_permissive）が **0件**
- 全体一致率 **98%以上**

これを満たすまで本番バッチを流さない。

## 既知の誤りの型（作成時点）

1. 検索の失敗を「情報が無い」として確定させる（花園公園: notes に
   「web検索は今回ツール上限により実施できず」と書きながら leashed_only）
2. 「記載なし」を「可」の方向に読む（断られる側の誤りのほぼ全て）
3. 公式サイトで探索を打ち切る（誤り8件は掲載系サイトに明記があった）
4. 条件（ケージ必須・抱っこ必須・サイズ制限）を落とす

## 2026-08-31 の実測（baseline）

`pet-policy-baseline.json` が実測の生データ。claude-sonnet-5 / 並列2 / タイムアウト120秒 /
preferWebSearch=true / git b310da3 / 40件・失敗0件（引き直し7件はすべて成功）。
実額 $4.38（$0.11/件）。

| | 2026-08-18（初版） | 2026-08-31 |
|---|---|---|
| 全体（README互換・undeterminable のみ除外） | 65.6%（21/32） | 53.1%（17/32） |
| 全体（除外ルールどおり・low も外す） | （初版は未算出） | 51.6%（16/31） |
| **主指標 飲食店・公園・ホテル** | **56.0%（14/25）** | **40.0%（10/25）** |
| 自明群（動物病院。ペットショップ1件は low で分母外） | — | 100.0%（6/6） |
| **db_too_permissive（40件が分母・同じ数え方）** | **17.5%（7/40）** | **10.0%（4/40）** |
| （参考）db_too_permissive・undeterminable を除いた分子 | — | 2.5%（1/40） |

誤りの向き（除外ルール適用後・31件）: 一致16 / db_too_permissive **1** / db_too_strict 1 /
db_unknown_but_knowable **13**。

**db_too_permissive を並べるときの注意。** 初版の 17.5%（7/40）は gold の `direction` を
数えたもので、7件のうち **5件は truth=undeterminable**（世に情報が無いのに db が
allowed / leashed_only と言い切った件）。除外ルール適用後の31件だけを分子にすると
1件（2.5%）になるが、それは分子の定義が違うので初版と並べられない。同じ数え方
（40件全体・undeterminable で言い切った件を含む）だと **4件・10.0%** で、
内訳は花園公園1件＋undeterminable を言い切った3件（鈴木鳥獣店 allowed /
フェリーチェガーデン日比谷 allowed / 千代田区立宮本公園 leashed_only）。
改善はしているが 17.5% → 2.5% ではない。JSON では
`of_all_40_same_basis`（比較用）と `of_all_40_excluding_undeterminable`（参考）を分けてある。

### 読み方

**一致率だけ見て「悪化した」と読まないこと。** 初版の65.6%は、本番パイプラインが時間をかけて
DBに積んだ値（`db_at_2026_08_18`）と gold の突き合わせ。今回はローカルで1回流した実測で、
外部検索プロバイダ（Brave / CSE）の鍵が無いぶん材料の集め方が違う。同じ土俵ではない。

**誤りの中身は変わっている。** 緩すぎ7件 → 1件、代わりに unknown が13件。
「記載なしを可の方向に読む」（既知の誤りの型2）は実質消えて、判定を保留するようになった。
飼い主が現地で断られる事故は減るが、地図には何も出ない。**どちらが良いかは別の問題**で、
ここは「精度が上がった」ではなく「誤りの型が入れ替わった」と記録する。

**残った db_too_permissive 1件は花園公園**（正解 not_allowed / 予測 leashed_only）。
既知の誤りの型1がそのまま残っている。出荷基準（飲食店・公園で db_too_permissive 0件・
一致98%以上）には届いていない。

**決定的上書きは1件も発火しなかった。** 飲食フォールバックは Web検索の成功が条件なので、
鍵の無い環境では構造的に発火しない。カテゴリ事前分布は LLM が unknown を返したときだけだが、
自明群6件は LLM 自身が全部当てたので出番がなかった。つまり今回は
「LLM素」と「ルール込み」が完全に一致している（どちらも 51.6% / 40.0%）。
**ルールの寄与を測るには鍵のある環境で回す必要がある。**

**条件の抽出は弱い。** gold の basis に条件（ケージ・抱っこ・サイズ制限）の記述がある8件のうち、
拾えたのは2件。既知の誤りの型4は手つかず。
