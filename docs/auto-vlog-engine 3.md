# 自動VLOG生成エンジン（SetLog × みてね型）— 戦略とロジック設計

作成日: 2026-07-08（改訂: 戦略背景の明文化と撮影リズム中心の再設計）
状態: **ロジック実装済み・未配線**（UI・通知・生成実行への接続は導入時に行う）
前提資料: `docs/setlog-vlog-improvement-proposal.md`（P1〜P8）、`docs/daily-log-design.md`

## 1. 戦略背景（この設計の前提。実装判断に迷ったらここに戻る）

### 参照モデルは2つ

**SetLog（記録メカニクス）** — 「1時間に1回、2秒だけ」の撮影リズムが1日に何度もアプリを開かせ、
1日の終わりに自動で1本のVlogが完成する。強制しない（撮れなかった時間は空くだけ）。

**みてね（コミュニティとLTV）** — 親が子供の写真・動画を上げる → 祖父母・家族が見て反応する →
親が通知を受けてまた上げる、という**往復ループが継続の本体**。「1秒動画」（自動生成のダイジェスト）が
定期報酬として機能し、フォトブック等のプレミアム転換につながる。

### 犬への翻訳と LTV 仮説

- **愛犬の扱いは子供に近い**。飼い主=親、家族・実家の親・散歩仲間=祖父母層（見る側）。
- 決定的な違い: 人間の子供は「子供の時期」が終わる（みてねの利用は成長とともに減衰する）が、
  **犬は生涯「うちの子」のまま**。記録と家族共有の需要が15年続く → **LTVは子供向けより高い**。
- バイラルはみてねより広い: 犬アカウント文化（#いぬすたぐらむ）があるため、
  クローズドな家族共有と並行して**外部SNSへの書き出し**が拡散エンジンとして機能する（SetLogのE5）。

### 記録フローの原型（旧カメラ時代の設計を継承）

廃止前のうつるんカメラ期に検証していた設計をそのまま原型とする:

1. **1時間に1回スロットが開き、最短2秒の動画を撮れる**
2. 撮ったものは**日常シーンタグで分類**（おさんぽ/ごはん/おひるね/おうち/おでかけ — `lib/daily-log.ts` の `DailyLogContext` と1:1）
3. **「おでかけ」タグのときだけスポット選択が出て、レビュー（★・メモ）を入れると
   VLOGに星評価とメモが反映される**（既存EDLの★加重尺配分・メモ字幕にそのまま接続）
4. **Weekly は Daily の延長線上の特別版**。独立したダイジェストではなく、
   その週の日次記録を素材に週間統計をまとった「今週のスペシャル」（みてねの1秒動画に相当する定期報酬）

## 2. パイプライン全体像

```
                 【日中: 撮影リズム = DAUの心臓】
  1時間1スロット ──▶ シーンタグ付き2秒動画 ──▶ visits/memories
  capture-rhythm.ts     （おでかけ時のみスポット+★レビュー接続）
        │ ナッジ（時間帯→タグ提案、強制しない）
        ▼
                 【夕方: 完成報酬 = E2の約束】
  ①エピソード分割 ──▶ ②生成可否判定 ──▶ ③提案スケジューラ ──▶ VlogOffer
   episode.ts           readiness.ts        scheduler.ts
   （Weekly=Dailyの特別版）                  （日曜夕方はDaily→Weekly昇格）
        │ 生成実行時
   既存: collectCandidates → selectCutsTwoLayerGate → buildEDL → render（無変更）
        │ 共有時
  ④共有キット share-kit.ts（キャプション・タグ・WM・犬プロフィールイントロ）
        │ 家族へ
  ⑤家族サークル family-circle.ts（みてね型往復通知・マイルストーン）
```

エントリポイントは `planAutoVlogs()`（`lib/vlog-auto/index.ts`）。
既存の `lib/vlog/`（品質ゲート・EDL・レンダリング）は一切変更せず import のみ。

## 3. 各モジュール

### 撮影リズム（`capture-rhythm.ts`）— DAUの心臓

- `buildCaptureDay`: きょうの1時間スロット表（7〜21時）。captured/open/passed/upcoming。
  アルバム先頭の常設UIとカメラ導線の状態源。連続記録ストリークも算出
- `suggestContextForHour`: 時間帯→シーンタグ提案（朝=おさんぽ、昼前=ごはん、昼下がり=おひるね、
  午後=おでかけ、夕=おさんぽ）。カメラを開いたときのデフォルト選択
- `planCaptureNudge`: プッシュはクールダウン2h＋1日3回まで（スロットは毎時開くが通知は間引く。
  リズムは作る・強制はしない）。文言はタグ別（「おさんぽの2秒、残しませんか 🐾」）

### エピソード分割（`episode.ts`）

| kind | 範囲 | 位置づけ |
|------|------|------|
| `daily` | きょう（時系列順=1日の物語） | 毎夕の定期報酬 |
| `weekly` | 月〜日 | **Dailyの特別版**。週間統計（記録日数・タグ内訳・スポット数・ベスト★）と素材元daily keys を保持 |
| `monthly` | 当月 | 月末のまとめ |
| `anniversary` | 1/3/6/12ヶ月前の同日 | 見返しトリガー（朝の時間帯） |
| `event` | イベント擬似スポットの当日 | resolver注入式（P7最小構成） |

### 生成可否判定（`readiness.ts`）

提案した以上は必ず見られる品質で返す（E2の信頼）。既存2層品質ゲートを流用して
ready / almost（「あと1枚」ナッジのみ）/ insufficient（黙る）の3段階。

### 提案スケジューラ（`scheduler.ts`）— 完成報酬の配達

- **報酬は出し惜しみしない**: 記録した日は毎夕18時以降に Daily が届く（1日1提案制限は廃止。
  制限するのは撮影ナッジ側であって報酬側ではない）
- **日曜夕方は Daily が Weekly スペシャルに昇格**（ready な weekly があれば daily を落とす）
- anniversary は朝〜日中で夕方の報酬枠と住み分け。event は即時
- クールダウンは「dismiss したものを連打しない」ためだけに使う

### 共有キット（`share-kit.ts`）— 外部バイラル

キャプション（犬名+スポット名）、ハッシュタグ（#wanspot #犬のいる暮らし #いぬすたぐらむ
#犬とおでかけ + 犬種 + イベント）、ウォーターマーク、犬プロフィールイントロ（P5）、アプリ誘導アウトロ。

### 家族サークル（`family-circle.ts`）— みてね型の往復ループ

- ロール: `owner`（飼い主）/ `family`（同居・パートナー）/ `extended`（実家の親・散歩仲間=見る側）
- 通知ループ: 新着は**見る側へバッチダイジェスト**（3hクールダウン、みてね同様まとめて）、
  **リアクション・コメントは投稿側へ即時**（継続の燃料なので間引かない）、
  Weekly スペシャル完成は**全員へ**（週1の「家族で見る」儀式に育てる）
- マイルストーン検出: 誕生日・記録日数の節目（7/30/100/365日）— 共有とプレミアム転換の山
- **データモデル（visits/memories の共有・RLS再設計）は未着手**のため、スキーマ非依存の
  純ロジックのみ。activities の取得・対象投稿主の特定はスキーマ確定後に置き換え

## 4. 導入時の配線ポイント（ここから先が実装フェーズ）

1. **撮影導線**: アルバムタブ先頭にスロット表UI＋カメラ起動（`suggestContextForHour` をデフォルトタグに）。
   おでかけタグ選択時のみ既存のスポット検索→レビューフローへ分岐
2. **通知**: captureNudge（日中）と offers[0]（夕方）を expo-notifications へ。既存 memory-anniversary と同枠
3. **生成実行**: offer 承諾 → `episode.plates` を既存 `buildVlogRenderPayload` → `render-client`（追加開発なし）
4. **状態永続化**: `AutoVlogSchedulerState` / `CaptureNudgeState` を AsyncStorage に
5. **サーバー前提修理（先行必須）**: P1（ファイル共有・WM焼き込み）と P2（BGM mux）。
   無音・共有不能のままでは自動生成してもバイラルしない
6. **家族サークルのスキーマ**: サークル・共有visits の RLS 再設計（P8）。それまで family-circle は型契約として待機
7. **イベント**: イベント擬似スポットのスキーマ確定後に `EventSpotResolver` を実装
