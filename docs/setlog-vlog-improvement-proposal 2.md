# Setlog体験の翻訳による「レビュー→自動Vlog」改善提案（改訂版）

作成日: 2026-07-02（改訂: 現行仕様の再確認を反映）
対象: wanspot（アプリ本体 + サーバー）のレビューアルバム / Vlog生成体験
目的: DAU向けアプローチとして「アルバム見返し」×「質の高い自動Vlog」×「SNSバイラル」の両軸を設計する

> 改訂メモ: 初版は「デイリーフォト（今日の1枚）」「写ルンです風カメラ」等、**既に廃止済みの機能**（dead code削除コミットで除去済み、作業ツリーに未追跡の残骸のみ）を現行機能として誤参照していた。本改訂版は、ルーティングから実際に到達可能な画面・実際に書き込まれるテーブルのみを「現行仕様」として扱う。

## 1. Setlog（セットログ）とは — 調査サマリ

参照: [nicola記事](https://nicola.jp/article/article-106758/)、PRESIDENT Online、AFPBB、Yahoo!ニュース等（2026年4〜6月）

- 韓国発のクローズドSNS。**「1時間に1回、2秒の動画を撮るだけで、1日分が自動で1本のVlogになる」**。2025年12月リリース、2026年4月に韓国App Store SNS無料1位、5月から日本のApp Store無料総合で連日1位。大学生の利用率5割・認知度7割という調査もある。
- 仕組み:
  - 1時間ごとに2秒動画を撮影(**強制ではない**。撮れなかった時間は黒画面になるだけ。BeRealのような「2分以内」の締切がない)
  - **最大12人のクローズドグループ(ログ)**で共有。フォロー/フォロワー概念なし。リアクション可
  - 1日の終わりに**書き出しボタンひとつでVlog完成**。編集スキル不要
  - 加工・フィルター不可 = 「盛らない」ありのまま共有
  - グループに入れず**自分だけのVlog**として使うことも可能
- 完成Vlogは Instagram 等に「#setlog」で大量に転載されており（縦型・2〜3分割画面のお出かけVlog）、**アプリ外SNSへの書き出しがバイラルエンジン**として機能している

### 刺さっている理由（体験設計のエッセンス）

| # | 要素 | 内容 |
|---|------|------|
| E1 | 超低コストの記録儀式 | 「2秒だけ」という制約が習慣化の障壁を極限まで下げる。完璧さを求めない |
| E2 | 自動報酬 | 記録するだけで「その日のVlog」という完成品が必ず手に入る。編集ゼロ |
| E3 | ゆるい時間トリガー | 1時間ごとというリズムが1日に複数回アプリを開かせる（=DAUの機構）。ただし強制しない |
| E4 | クローズドな共同制作 | 親しい少人数と「1日の思い出ストーリーが積み重なる」。見る動機と撮る動機が相互強化 |
| E5 | 外部SNSへの書き出し | 完成Vlogをそのまま Instagram 等へ。アプリ内に閉じない拡散設計 |
| E6 | 見返しの楽しさ | 「後からこんなことあったなって見返すのが楽しい」（ニコ読アンケート）— アーカイブ自体が資産 |

補足: `lib/vlog/set-log.ts` の `MediaSetLog` は品質メタデータ機構に名前を借用したもので、本提案で扱う「Setlogの体験」はアプリとしてのUX全体を指す。

## 2. wanspotの現行仕様 — レビュー→Vlog体験

### 現行の体験フロー（到達可能な画面ベースで確認済み）

現行アプリの記録体験は**「スポット評価＋ひとことメモのレビューに、Vlog用の写真・動画を添付する」のみ**。日次撮影・デイリーフォトのような独立した撮影機能は存在しない。

1. **行った記録**: スポット詳細画面（`SpotDetailScreen`）の「行った記録」ボタン → `visits` テーブルにinsert（同日・同スポットは1回）。アクションシートから「レビューをアルバムに残す」でアルバムタブへ誘導
2. **レビュー投稿**: アルバムタブ（`ReviewAlbumTimeline` のカードデッキ）→ レビューコンポーザー（`MemoryComposerModal`）で以下を1つの「レビュー」として保存:
   - ★評価（1〜5）→ `visits.rating`
   - ひとことメモ（最大500字）→ `visits.comment`
   - 写真・動画 最大10点 → Supabase Storage `memories` バケット + `memories` テーブル（visit・spotに紐付く）
3. **Vlog化**: 液体ゲージ（5スポット×メディア2点でアンロック演出）→「Vlogを作る」でレビューを複数選択 → 生成（クラウド品質解析 → 2層品質ゲートでカット選定 → EDL構築 → サーバーFFmpegレンダリング）
4. **プレビュー・共有**: `app/vlog/preview.tsx` で再生 → OS共有シート

### 技術的な土台（できていること）

- **EDL v9.5**: 120BPMビート同期、カット2〜3拍、★加重の尺配分、rankScore（品質+動き+感情+構図）によるカット選定・ピーク検出、ひとことメモのオーバーレイ字幕、スポット名チップ、Ken Burns、動画の頭ブレ回避trim、救済カット
- **出力は既に縦型 9:16（1080×1920）**、尺は10〜35秒に自動クランプ
- ムードに応じた選曲ロジック（跳ね系/ほっこり系/元気系の3トラック）— ただし後述G1の通り音は出ていない
- サーバー側にはイベント関連API（作成・モデレーション・サムネ生成・Stripe決済）が存在するが、**アプリ側のイベントUIは廃止済みで現行バージョンには存在しない**

### ギャップ（Setlog比 + 実装上の穴）

| # | ギャップ | 詳細 |
|---|---------|------|
| G1 | **BGMが実際には鳴っていない** | クライアントは選曲・ビート同期EDLを作るが、サーバー `render-edl.ts` は全行程 `-an`（音声破棄）で、**BGMの合成処理が存在しない**。無音の動画が出力されている。トランジション`white_flash_2f`もEDL上の宣言のみで未実装（単純concat） |
| G2 | **共有がURLテキスト共有** | `Share.share({ url: remoteUri })` で**7日で失効する署名付きURL**を共有。動画ファイルとしてSNSに投稿できず、カメラロール保存もない。ウォーターマーク/アプリ誘導もなし |
| G3 | **日次の記録・開封トリガーが存在しない** | 記録の入口が「スポットに行った」に限定され、Vlogも「5スポット貯めて作る」設計。お出かけしない日にアプリを開く理由・撮る理由がゼロ（E1/E3の不在）。日次撮影機能は過去に試作されたが廃止済み |
| G4 | 生成が手動・多段階 | 選択→生成のステップが必要。Setlogの「記録すれば自動で完成品」（E2）に対し摩擦が大きい |
| G5 | 共同性がない | Vlogは完全ソロ。家族・散歩仲間・イベント参加者と「積み重ねる」体験（E4）がない |
| G6 | 演出の固定 | イントロ/アウトロは黒背景+白文字のみ。犬プロフィール演出、シーズナルフレーム、テンプレ選択なし |

## 3. 改善提案（優先度順）

### P1. 共有導線の作り直し — ファイル共有 + カメラロール保存 + ウォーターマーク 【S〜M】
- **概要**: プレビュー画面で (a) mp4をローカルDLして `expo-sharing` でファイルとして共有シートへ、(b) `expo-media-library` でカメラロール保存、(c) レンダー時に控えめなウォーターマーク（右下に `wanspot` ロゴ + 犬名 🐾）とアウトロにアプリ誘導カード（QR/ストア名）を焼き込む。
- **Setlog翻訳**: E5（外部SNSへの書き出しがバイラルの本体）。Setlogも「書き出し→Instagram転載」で伸びた。
- **期待効果**: バイラル。現状は共有が実質機能していない（失効URL）ため、これが全バイラル施策の前提。
- **実装**: 既存FFmpegパイプラインに `overlay` / `drawtext` 追加のみ + アプリ側は共有処理の差し替え。**新規技術なし**。

### P2. BGM合成とトランジションの実装 — 「無音Vlog」の解消 【M】
- **概要**: ライセンス済み3トラックの音源ファイルをレンダーワーカーに配置し、EDLの `track` に従って (a) BGMをmux（尺に合わせてフェードアウト）、(b) 宣言済みの `white_flash_2f` トランジションを実装、(c) ピーク区間（`peakStartBeat`）と曲のサビ（`peakOffsetBeats`）を頭出しで合わせる。
- **Setlog翻訳**: E2（自動で「ちゃんとしたVlog」が手に入る）。無音動画はSNSに投稿されない。ビート同期EDLは既にあるので、音が付くだけで体感品質が一段変わる。
- **期待効果**: バイラル（共有したくなる品質の最低条件）+ 見返し体験の質。
- **実装**: FFmpeg `amix`/`afade` + faststart。クライアント変更ほぼ不要（EDLに全情報あり）。

### P3. 「きょうのログ」— 日次記録の仕掛けを新規に作る 【M〜L】
- **概要**: **新規機能**として、スポット訪問に依存しない日次のクイック記録を作る。散歩・おうち時間に「2秒動画 or 写真1枚 + 気分スタンプ」だけを残せる超軽量の記録導線をアルバムタブ先頭に常設し、素材は当日の擬似visit（「散歩」「おうち」等の内部スポット扱い、または `visits.spot_id` をnullable化した日次ログ行）として `memories` に保存 → **そのまま既存のVlog素材プールに入る**。
- **Setlog翻訳**: E1（2秒だけ、完璧を求めない）+ E3（1日複数回のゆるいトリガー）。犬の飼い主への翻訳は「1時間ごと」ではなく**「散歩・ごはん・昼寝」という犬の生活リズム**。
- **期待効果**: **DAU**（お出かけしない日にも撮る理由・開く理由ができる）+ Vlog素材の量と鮮度が上がり生成率も向上。
- **実装規模の注記**: メディアアップロード（`uploadMemoryFile`）・`memories` テーブル・品質ゲートは全て流用できるが、撮影UI・擬似visitのデータモデル・アルバム上の表示は**ゼロから作る**（初版で「既存デイリーフォトの拡張M」としたのは誤り。該当機能は廃止済み）。スキーマ変更を含むためM〜L。
- **設計上の教訓**: 過去に「1日1枚のデイリーフォト」が試作→廃止された経緯がある。廃止理由（レビュー体験と分断されていた点が有力）を踏まえ、今回は**独立アルバムを作らず、最初からVlog素材プール＝レビューアルバムに合流させる**ことを必須要件とする。

### P4. 「1年前の今日」「今週のふりかえり」— 見返しトリガーの自動化 【S〜M】
- **概要**: (a) `visits`/`memories` から「◯ヶ月前の今日、△△に行ったね」を毎朝ローカル通知 + アルバム先頭にメモリーカード表示。(b) 週末に「今週の思い出が◯件。30秒のダイジェストにする？」→ タップで既存パイプラインにそのまま流す**週次ダイジェスト半自動生成**。素材が2件でも既存の救済カット機構で成立する。
- **Setlog翻訳**: E6（見返し自体が楽しい）+ E2（勝手に完成品ができている感覚）。
- **期待効果**: **DAU**（通知→開封→見返しの習慣ループ）。**現行の visits/memories データだけで動く**ため費用対効果が最も高い。P3と違い新規の記録行動を要求しない。
- **実装**: クライアント側の集計 + expo-notifications。サーバー変更ほぼ不要。

### P5. 犬プロフィール演出 + シーズナルテンプレート 【M】
- **概要**: イントロを黒背景文字から**犬のプロフィールカード**（アイコン写真・名前・犬種・「◯歳△ヶ月のおでかけ記録」— 既存の犬プロフィールデータを流用）に差し替え。季節・イベント時期に応じたフレーム/カラーグレード/装飾のテンプレを2〜3種用意し、生成前に1タップで選択（デフォルトは自動）。
- **Setlog翻訳**: nicola記事の後半「かわいい撮り方テク」— 若年層は**テンプレに乗るだけで可愛くなる**ことに価値を感じる。犬の飼い主にとっての「うちの子が主役」演出。
- **期待効果**: バイラル（共有時に「これ何のアプリ?」となる固有の見た目）+ 生成満足度。
- **実装**: イントロカードのFFmpeg合成（犬アイコン画像のoverlay）+ テンプレ定義（LUT/フレームPNG）。フィルター素材は新規制作が必要（初版で流用候補としたフィルター実装は廃止済み。必要ならgit履歴から参照は可能）。

### P6. レビュー保存→ワンタップVlogの摩擦削減 【S】
- **概要**: レビュー保存完了時に「このレビューでVlogにする？」を即時提案（対象1件で即生成、尺短めでOK）。また月末に「今月のVlogができます」と自動で選定済みプレビューを提示し、ユーザーは確認→生成のみ。選択UIはパワーユーザー向けに残す。
- **Setlog翻訳**: E2（書き出しボタンひとつ）。現状の「選んで作る」から「できているものを受け取る」への転換。
- **期待効果**: 生成率向上 → 共有母数の増加（バイラルの分母）。
- **実装**: 既存の自動選定ロジック（2層ゲート）をそのまま適用するだけ。UI変更中心。

### P7. イベントVlog — オフラインイベントとの接続 【L】
- **概要**: 自社オフラインイベント会場で撮った素材がそのままVlogになる体験。会場QR等でイベント用の擬似スポットにチェックイン → 会場で撮った写真・動画を通常のレビューフローで投稿 → **イベント名義の演出（イベントロゴ入りイントロ/フレーム）付きVlogが自動生成**され、共有ハッシュタグ（#wanspot #イベント名）付きで書き出せる。
- **前提の注記**: サーバー側にはイベントAPI（作成・モデレーション・決済等）が残っているが、**アプリ側のイベントUIは廃止済みで存在しない**。本提案はアプリ内イベント機能の再構築を待たず、「イベント=特別な演出が付くスポット」という最小構成で始められる設計とする（イベント専用画面を作らない）。
- **Setlog翻訳**: E4（同じ場にいた仲間との共同の思い出）のイベント版。参加者の共有動機が最も高い瞬間を捕まえる。
- **期待効果**: バイラル（イベント直後の一斉SNS投稿）+ イベント集客との相互送客。
- **実装**: イベント擬似スポットの管理、イベントテンプレ演出、QRチェックイン導線。

### P8. 家族・散歩仲間との共有アルバム（グループログ） 【L・将来】
- **概要**: 犬1頭に対して家族など少人数（Setlogに倣い上限を小さく）を招待し、レビュー/写真を持ち寄って**共同のアルバム＆Vlog**を作れるようにする。リアクション機能を付ける。
- **Setlog翻訳**: E4の本丸。「クローズドで犬の成長を積み重ねる」は多頭・家族飼いに強く刺さるが、visits/memoriesが完全にユーザー単位の現行データモデル（RLS含む）の再設計が必要。
- **期待効果**: DAU（家族の誰かが投稿→通知→開く）+ 招待による自然な新規獲得。
- **実装**: マルチユーザー共有のスキーマ・RLS再設計。P3/P4の成果を見てから着手を推奨。

## 4. 最初の2週間でやるべきもの

**推奨: P1 + P2 + P4（の通知部分）を同時並行**（改訂前と変更なし。いずれも現行の visits/memories/EDL 基盤のみに依存し、今回の現状認識の修正による影響を受けない）

| 週 | やること | 理由 |
|----|---------|------|
| 1週目 | **P1**: ファイル共有・カメラロール保存・ウォーターマーク / **P2**: BGM mux実装 | バイラルエンジンの前提修理。今のVlogは「無音・共有不能」なので、他のどの施策より先。両方とも既存FFmpeg/EDL土台の延長でリスクが低い |
| 2週目 | P2の仕上げ（トランジション・サビ頭出し）/ **P4a**: 「◯ヶ月前の今日」通知 + アルバム先頭のメモリーカード | P4aは現行データのみで動く最小のDAU施策。通知→アルバム→（P1/P2で良くなった）Vlog共有、というループの最初の1周を完成させる |

この2週間で「**作ったVlogがちゃんと音付きでSNSに投稿でき、毎朝アルバムを開く理由がある**」状態になる。その後、効果を見ながら **P6（ワンタップ化・S）→ P3（日次記録・M〜L）→ P5 → P7** の順で拡張するのを推奨する。P3は規模を上方修正（既存土台なし）したため、小さいP6を先に回すのが改訂後の推奨順。
