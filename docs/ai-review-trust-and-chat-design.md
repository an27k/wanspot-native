## 0. 結論サマリ

1. **「信用できない」は体感でなく実測。** gold set（`eval/pet-policy-gold.json`、東京40件・根拠URL付き）で、飲食・公園・ホテルの同伴可否精度は **56.0%**、現地で断られうる誤りが **17.5%**。
2. **誤りの型は5つに特定済みで、うち2つはプロンプトでなく決定的コードで潰せる**（検索失敗のまま確定／出典の捏造）。精度改善はギャンブルではなく、失敗モード別の対策リストになっている。
3. **確度可視化の部品はDBに揃っている**が、APIレスポンスに一切載っていない。後方互換な追加フィールド1つで両OSに安全に出せる。
4. ただし実分布は厳しい: 確定ステータス16,194件のうち**確度「低」相当が約10,900件（67%）**。バッジを今すぐ全面表示すると「推定を含みます」だらけになる。ここが最大の相談ポイント（§5）。
5. **チャットは既存資産の再結合でMVPが作れる**。削除済みAIプランのSSE骨格（git履歴に現存）＋既存の認証・レート制限・コスト枠。スポット詳細に閉じたQ&A・検索なし・注入のみなら、**sonnet-5 で1会話約$0.02、MAU 1,000で月約$80、日次$5枠で月$155に頭打ち**。
6. チャットの構造的な強み: AIレビューは共有キャッシュ制約で犬情報をプロンプトに入れられないが、**チャットは応答がuser単位（共有キャッシュに載らない）なので犬プロフィールを自由に使える**。「うちの子の話をしている」温もりはチャット側でこそ出せる。

## 1. 現状の実装（検証済みの事実）

### 生成パイプライン
- `/api/ai-summary`（1,169行）。モデル `claude-sonnet-5`（env切替可、フォールバック `claude-sonnet-4-5-20250929`）、thinking明示OFF。
- **深い版**（Anthropic server-side `web_search_20250305`, max_uses:3）と**速い版**（検索なし）の二段競走。初回表示予算12秒。間に合わなければ浅い版を `search_state='pending'` で返し、`after()` と読出時再試行（上限3回）で昇格。
- 共有キャッシュ `ai_cache`、key=`ai-summary:v2:<placeId>`、TTL 90日。**犬情報は厳禁**（先に開いた人の犬種が全員に配信される事故防止）。`personalNote` はLLM不使用・毎回決定的算出。
- 未検証スポットは閲覧が検証トリガー（`verifySingleSpot`、待ち6秒、超過時は裏で完走）。
- 在庫の**69%が検索なし浅い版**（中央値153字 vs 検索つき319字）。

### 確度の既存部品（DBにあるがAPIに未出力）
- `pet_friendly_confidence`（confirmed/inferred）— LLM自己申告を notes の推測語 regex で上書き（自己申告だけでは信用しない実装が既にある）
- `source_label` 4値 + `source_url`
- `pet_policy_evidence`（official/aggregator/reviews/inferred）— DB列ではなく source×confidence から応答時計算
- 制約: **「検索が失敗した」と「調べたが情報なし」がDB上で区別できない**（最重要の欠落信号）

### 実測分布（2026-08-18、確定ステータス16,194件）※要SQL再取得
- official×confirmed ≈ 2,584（→高候補）
- confirmed×掲載/口コミ ≈ 2,726（→中候補）
- inferred 合計 ≈ 10,884（→低。**多数派**）
- 「verified=true だが実質推測」が大量に存在。verified は「検証を試みた」フラグであり信頼指標ではない。

### 失敗モード（gold set 実例）→ 対策
| # | 失敗モード | 実例 | 対策の型 |
|---|---|---|---|
| 1 | 検索失敗を「情報なし」として確定 | 花園公園（notes に「検索できず」と書きながら確定） | **決定的**: 検索失敗時は status を unknown に強制＋新列 `pet_search_outcome` に記録 |
| 2 | 「記載なし」を可の方向に読む | 明治神宮境内カフェ（境内一律禁止なのに outdoor_only 推定） | プロンプト＋スキーマ: 非unknown には出典URL＋50字以内の原文引用を必須化。親施設ルール追加 |
| 3 | 公式サイトで探索打ち切り | EDEN（ホットペッパーに「ペット可」明記なのに unknown。同型8件） | ツール: 掲載系サイトの検索指示＋`web_fetch` で spots.website を直接読む |
| 4 | 条件（ケージ必須等）の落とし | Mary Jane | プロンプト＋eval指標化 |
| 5 | 出典の捏造 | SIDEWALK COFFEE（独立調査で発見できない口コミ根拠） | **決定的**: source_url を検索結果URL集合と照合、不一致は inferred へ強制降格 |

検証で入った重要な訂正: 対策5の照合対象は Anthropic `web_search_tool_result` だけでは**不十分**。検証の主経路は Brave / Google CSE で、LLM web_search は代替経路のみ。**外部検索プロバイダの結果URLも照合集合に含めないと、新列がほぼ null のまま機能しない。**

## 2. 施策1: 精度改善と確度可視化

### 2.1 確度スコア
- **3段階（高/中/低）・決定的計算・LLM不使用・犬情報非依存**。応答時に毎回計算、キャッシュ非保存（personalNote と同じ層）。
- 数値スコアは作らない（gold 32件では較正不能）。LLM自己申告の生値も使わない。
- 新列2つ（nullable・埋め戻しなし）: `pet_search_outcome`（succeeded/failed/not_run/no_results）、`pet_evidence_url_verified`。null は「不明」として保守側。
- 判定: 検索失敗 or inferred or 未検証 → 低。official×URL照合通過 or 自明カテゴリ（ドッグラン・動物病院・ペットショップ） → 高。それ以外（掲載/口コミで裏取り）→ 中。`search_state='pending'` は中でキャップ。

### 2.2 API変更（後方互換・厳守事項）
```typescript
// AiSummaryApiResponse にトップレベル新規オプショナルを追加
confidence?: {
  level: 'high' | 'medium' | 'low'   // クライアントは String で受け、未知値は非表示
  evidence?: 'official' | 'aggregator' | 'reviews' | 'inferred'
  sourceLabel?: string
  lastCheckedAt?: string             // 表示は「YYYY年M月」粒度
  sourceCount?: number
}
```
- **既存 `searchState` / `emptyReason` の列挙値は絶対に増やさない。** Swift 2.0.0 は enum 直デコードで、未知値1つで応答全体の decode が throw →「混み合っています」表示に化ける。
- Swift 側の新フィールドは enum でなく String で受けて init 内マッピング（emptyReason の先例）。
- クライアントキャッシュキー（RN/Swift とも v2）は上げない。旧キャッシュはバッジ無し表示で正しく、TTL 30分で自然置換。
- 互換対象は3系: **RN 1.0.2 / Swift 2.0.0 / Swift 2.0.1 (262)（現行）**。

### 2.6 低確度 → 情報提供ループ（決定済み・要デザイン）

低確度バッジは「謝って終わり」ではなく**情報の入口**にする。既存資産で導線の大半が組める。

**既存資産（確認済み）**
- `spot_info_tips`: 投稿テーブル実在。書き込み専用（SELECT は本人にも開けない = 書き手特定を防ぐ意図設計）。Swift に投稿シート実装済み（`SpotDetailSheets.swift` 「犬連れ情報を教える」、`SpotDetailStore.submitInfoTip`）。現在の入口は AIレビュー空のときのみ（`source` check 制約が `'ai_review_empty'` の1値）
- `spot_dog_facts.source` に **`owner` が既に語彙として存在**（spots_column / pet_amenities_parse / verify_llm / **owner** / official）。構造化された飼い主情報の置き場は最初から設計されている

**設計**
1. **入口の拡張**: 低確度バッジの展開部に「行ったことがありますか？情報を教えてください」ボタン → 既存 tips シートを開く。`spot_info_tips.source` の check 制約に `'low_confidence_badge'` と `'chat_no_answer'` を追加する migration（1本）。チャットが「わからない」と答えたときも同じシートへ誘導（§3 と共通導線）
2. **自由記述だけでなく構造化質問を前段に置く**: シート冒頭に、そのスポットで unknown / 低確度の fact_key から3〜5個をチップ提示（「店内に入れましたか？」「足洗い場はありましたか？」→ はい/いいえ/わからない）。回答は `spot_dog_facts` へ `source='owner'` で書き（**クライアント直書きではなく Next.js API＝service_role 経由**。`spot_dog_facts` の RLS は service_role 専用のため）、自由記述は従来どおり `spot_info_tips` へ。**単独報告は confidence='inferred' 扱い、複数ユーザーの一致で 'confirmed' へ昇格**（新しい confidence 値は追加しない = 互換維持）
3. **貢献の可視化**: バッジ内訳に「飼い主さんの情報 n件」を件数のみ表示（原文非公開・書き手特定回避の既存方針を維持）
4. **検証キューとの接続**: owner 報告のあるスポットは再検証の優先度を上げる（「どこを裏取りに行けばよいか」が分かっている状態は検証成功率が高い）

**ループ**: 低確度表示 → 情報提供 → dog_facts(owner) → 検証優先 → 確度上昇 → バッジ改善。チャットの「わからない」も同じ入口に流し込む。**低確度の正直な表示が、そのままデータ収集の駆動力になる。**

## 3. 施策2: AIチャットアシスタント（Swift版のみ）

### 3.1 MVP設計
- **1ターン=1リクエストのSSE**。LLM呼び出しはツール不使用ターン（画面文脈の注入で足りる質問）で1回、ツール使用ターンで2回以上。会話は**サーバ保存する**（§3.7、当初案の「保存なし」から決定変更）。クライアントはシート表示中メモリ保持＋再訪時にサーバから直近セッションを復元。
- **チャットの顔はマスコット（白いロボ犬キャラ）**。FABのアイコン・シートのヘッダー・アシスタント吹き出しのアバター・空状態/上限カードに一貫して使う。**キャラデザ本制作は外注予定**。それまでは既存画像の切り抜きを仮アセットとして使用（丸抜き・サイズ違いは実装側で clipShape）。
- **入口は画面右下に常駐するフローティングボタン**（56pt・マスコットのグラデ円ボタン）。タップでチャットシートが開く。**FAB上のポップ吹き出しは出さない**（文脈に合う一言をリアルタイム生成するのは非現実的、という判断。2026-08-30）。文脈の違いはシート内のサジェスト質問チップで表現する。AIレビュー直下のインラインボタンは置かない。
- **全画面常駐・全対応**（2026-08-30 決定）。FABは**ログイン後の全画面**に出す（未ログイン画面のみ非表示 — 相談枠が個人単位のため）。チャットは1つのグローバルアシスタントで、どの画面からでもスポット・エリア横断・イベント・記事・自分の記録に答える。
- **会話は「ワンスポAI」1本・ヘッダー固定**（同日追記）。画面ごとにシートのタイトルや会話を切り替えない（切替の重さ・遅さを排除）。開いている画面の文脈はメッセージ送信時に `context` として透過的に添えるだけで、UI上はサブタイトルの「いま見ている: ◯◯」とサジェストチップにのみ現れる。**画面は根拠の境界ではなく「メッセージに添える文脈」**:

| 開いた画面 | 事前注入される文脈（ツール往復の節約） | シート内サジェストチップの例 |
|---|---|---|
| スポット詳細 | そのスポットの全FACTS（最頻ケース。LLM1回で完結） | 「店内に入れる？」「駐車場はある？」 |
| 地図/検索タブ | 地図中心の lat/lng＋半径（既存 nearby と同型） | 「テラスOKのカフェ」「ドッグラン」 |
| カレンダー詳細 | そのイベントの事実 | 「犬連れで参加できる？」 |
| 記事 | 記事のリンク先スポット群 | 「この中で雨でもOKなのは？」 |
| マイページ等（文脈なし） | ユーザー文脈のみ | 「次のおでかけ先を相談」 |
- **注入＋tool use のハイブリッド**。MVPから**DB参照ツール4本＋提示ツール3本（スポット/記事/イベントのカード提示）＋条件付き web_search** を持つ。DB参照: `get_spot_facts(spot_id)` / `search_spots(lat, lng, radius, filters)`（既存 nearby 基盤のパラメータにそのまま合わせる） / `get_event(event_id or date)` / `get_articles(topic)`。開いた画面の文脈は事前注入し、最頻ケース（スポット詳細でその店のことを聞く）はツール往復なしのLLM1回で完結させる。ハルシ対策の原則は「注入FACTSに無ければ言わない」から「**ツール結果に無いことは言わない**」へ一般化。横断検索の回答は文章＋スポットカード（詳細へのディープリンク・確度バッジ継承）で返し、確認のとれたスポットだけを提案する。Web検索は**条件付きで解禁**（2026-08-30 方針転換）: 内部ツールで答えが見つからない場合のみ `web_search`（max_uses 2）を許可し、「情報を持っていません」で突き放さず調べて答える。ただし**出所ラベルを義務化** — Web由来の回答には「※Web検索の情報を含みます（未確認）」を必ず付加し、同伴可否・健康・安全・料金など実害があり得る情報は根拠の種類を文中明示＋確認を促す。検索クエリに個人情報（犬の名前等）を入れない。
- SSE骨格は削除済みAIプランルートを復元流用（`git show 26bccf0~1:src/app/api/ai-plans/generate/route.ts` に認証・レート制限・同時実行制限・finally解放の完成形）。新規に書くのは Anthropic SDK `messages.stream` → SSE の結合部のみ。
- **ログイン必須**（AIレビューと同じゲーティング）。ゲストクォータは anonymous_id 偽造可能なため LLM 課金機能には転用しない。「聞くにはログイン」は導線としても好適。

### 3.2 グラウンディング
- FACTS注入: `spot_dog_facts` 16キーを **unknown 込みで全量**注入（AIレビューの yes のみ注入とは逆設計。「無いことを答える」機能だから）。検証指摘: 行が無い=未調査 と value=unknown=調べたが不明 の3状態なので、**欠損キーは「未調査」として合成**してから渡す。
- 営業時間はLLMに計算させない。サーバでJST整形した文字列を渡し、Swift 側にネイティブ営業時間UIを併記。
- `confidence=inferred` の事実は「〜のようです。念のためご確認ください」形を強制。`canStatePetPolicy=false` のスポットは同伴可否の断定を全面禁止。
- 確度チップはLLMに言わせず、サーバが決定的計算して**SSE先頭の `meta` イベント**で送る。語彙は施策1と共通モジュール化。
- ストリーム完了後の最終検査: 「弱い根拠×断定語」の組合せを regex 検出し、注意書きフッターを追記。
- 品質eval（想定質問×FACTS導出正解×「わからないと言うべき質問」）を**生成スクリプトごとコミット**し Batch API（50%引・トークン分のみ）で回す。合格基準「FACTS外の店舗固有断定 0件」。

### 3.3 SSE契約（将来互換を最初から）
```
data: {"type":"meta","grounding":{...},"quota":{"remainingToday":18}}
data: {"type":"delta","text":"はい、"}
data: {"type":"limit","code":"daily_quota","resetAt":"..."}
data: {"type":"done","turnId":"..."}
```
- Swift は `type` を String で受け**未知typeは読み飛ばす**（searchState 事故の契約レベル再発防止）。
- チャット用に `timeoutIntervalForRequest=120` の別 URLSession（既存の12秒/40秒予算はストリームと相容れない）。`URLSession.bytes(for:)` で外部ライブラリ不要。

### 3.4 コスト制御（過去事故の教訓を反映）
| 層 | 値 |
|---|---|
| operation | `'ai-chat'` 新設 ＋ SEPARATE_BUDGET_OPERATIONS へ追加（急増しても他の自動化を巻き添え停止しない・されない） |
| 日次ドル枠 | `AI_CHAT_DAILY_CAP_USD` = **$5/日**（月 ≈$155 ハードシーリング） |
| 件数枠 | 3,000往復/日（ドル枠 fail-open の二重受け） |
| ユーザー枠 | **20往復/日**（理論上限 $0.10/人/日）＋10メッセージ/分＋同時1ストリーム |
| 入力制限 | 1メッセージ500字・履歴10往復・max_tokens 512 |
- **見せ方（2026-08-30 決定）: 数字は非宣伝・実質無制限として提供する。**「無料で使えます」とだけ言い、回数制限の存在は残3回の予告表示まで一切出さない。上限は課金対策ではなく「1人の暴走から共有枠と他ユーザーを守る」仕組み。リリース後に実測 p99 を見て、上限接触者が想定より多ければ 30〜50/日 へ広げる（絞る方向の変更はしない）。将来の有料プラン（無料20/日＋プレミアム無制限）のレバーとして温存。
- 上限到達は 429 でなく SSE `limit` イベント →「今日の相談枠を使い切りました」カード。残3回からUI表示。
- 検証指摘: 同時1ストリームは **releaseStream 漏れ＝そのユーザー恒久締め出し**。finally 解放に加えロックTTLを付ける。

| **sonnet-5** | **$0.03〜0.04** | **$12〜16/月** | **$120〜160/月** | $1,200〜1,600/月 |

| Phase | 内容 | ゲート |
|---|---|---|
| 0 MVP | **全画面FAB＋全対応チャット**: ツール4本（spot_facts / search_spots / event / articles）＋画面文脈の事前注入＋会話保存＋分析基盤（§3.7）。旧計画の「横断検索は Phase 2」は前倒しで統合 | — |
| 1 | 「うちの子」文脈強化 — **実装済み 2026-08-31**: 飼い主ペルソナの静的ルール化＋登録情報（犬プロフィール・行動圏・直近visits）の毎回注入＋**継続メモリ**（下記） | ✅ |
| 2 | ツールの深掘り: 営業時間ベースの「今から行ける」、混雑傾向、リストへの追加などアクション系の参照拡張 | 実ログの質問分布 |
| 3 | プラン提案（旧ai-plans復元） | 利用の定着 |
| 4 | **予約コンシェルジュ**: 店舗側管理画面（別プロダクト）と連携し、空き確認→提案→予約確定まで会話内で完結 | 店舗管理画面の存在＋導入店舗 |

全対応化の代償は2つ: (a) MVP実装にツールループが入る（+1週間程度、無限ループ対策・ツール失敗時の応答設計を含む） (b) ツール使用ターンはLLM呼び出し2回になりコスト増（§3.5の改訂値）。どちらも受容して前倒しする判断（2026-08-30）。

**Phase 4 の設計原則（MVPが今決めておくべきガードレール）**

予約は取引であり、ハルシネーション許容度ゼロ。LLMは会話の殻に徹し、事実と操作は全部ツール側に置く。

1. **参照系と更新系のツールを分離**: 空き照会（参照）はLLMが自由に呼べる。予約作成（更新）は**LLMが直接実行できない**。LLMは `action_proposal` を出すだけで、実行はユーザーが構造化確認カード（日時・人数・犬情報・キャンセル規定を定型表示）のボタンを押したときにサーバが行う。自由文で「予約しました」と言わせない
2. **SSEイベント契約は既に拡張可能**（未知type読み飛ばし規約）。Phase 4 で `action_proposal` / `action_result` イベントを足しても旧クライアントは壊れない — MVPの契約設計がそのまま効く
3. **会話保存（§3.7）が予約の監査証跡になる**: 「言った/言わない」紛争時に会話とアクション実行ログを突き合わせられる。予約確定は chat_messages ではなく専用の bookings テーブルに正規化して記録（会話ログは補助証跡）
4. **需要データが営業資材になる**: §3.7 の質問分類に**予約意図（reservation_intent）を初日から含める**。「あなたの店はワンスポで月n回、犬連れ予約の相談をされています」は店舗管理画面を売る最強の営業トークで、Phase 4 のずっと前から蓄積だけしておける
5. 外部予約サービス（食べログ等）のAPI連携は前提にしない。予約在庫は自前の店舗管理画面が持つ（外部APIは閉鎖的で、依存すると製品の存立が他社判断に握られる）

### 3.7 会話の保存とデータ活用（決定済み）

**方針**: 保存する。表の価値はパーソナライズ（会話の継続・再開）、裏の価値はプロダクト分析。ただし「裏」を裏のままにしない — 後述のとおり、**両方の目的を利用目的に明記すれば二枚舌は不要**で、明記しない場合だけが法務・審査リスクになる。

**スキーマ**
```sql
create table chat_sessions (          -- 会話スレッド。ユーザーにつき実質1本（無操作で一定期間あいたら新スレッド）
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  dog_id uuid,
  started_at timestamptz not null default now(),
  last_message_at timestamptz not null default now()
);
create table chat_messages (
  id uuid primary key default gen_random_uuid(),
  session_id uuid not null references chat_sessions(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  role text not null check (role in ('user','assistant')),
  content text not null,
  context jsonb,            -- 送信時に開いていた画面の文脈 {screen, place_id?, lat?, lng?, radius?, event_id?, article_id?}
  grounding jsonb,          -- metaイベントで送った確度スナップショット
  model text,
  input_tokens int, output_tokens int,
  created_at timestamptz not null default now()
);
```
- スポット単位のセッションは持たない（画面を移動しても会話は続く）。文脈はメッセージ単位の `context` に記録し、分析（§の質問分類）もここを軸に集計する。

**継続メモリ（2026-08-31 追加・ユーザー決定）**
- `chat_user_memory`（user_id PK, content ≤2000字, updated_at）。毎ターン後に `after()` で **claude-sonnet-5** が現ノート＋今回の往復から**恒久的な事実だけ**を抽出しノート全体を書き直す（変更なしは NO_CHANGE でスキップ）。次ターンから system 第2ブロック（per-userキャッシュ）に注入。
- 覚えるもの: 犬の性格・苦手・好み、飼い主の移動手段・時間帯の傾向など、おでかけ相談に役立つ恒久情報のみ。**覚えないもの: 健康の診断的記述・センシティブ情報・一時的な話題・推測**。矛盾は新しい方、古い項目は削除。
- プライバシー: 本人SELECT可（将来「AIが覚えていること」画面で開示・編集できる設計余地）、書き込みは service_role のみ、退会時削除。メモリはベストエフォート（更新失敗で会話は止めない）。
- コスト: sonnet-5 で ≈$0.005〜0.013/往復の追加。既存 'ai-chat' 枠（$5/日）内。
- RLS: 本人 SELECT のみ（継続・再開に必要）。INSERT は service_role のみ（サーバが書く。クライアント直書きは偽造の余地）。
- **ai_plans の FIFOトリガー方式は使わない**（5件FIFOが履歴長と競合する既知の指摘）。保持は期間制で cron 削除。
- **account/delete への追加が必須**: 削除ルートは手動テーブル列挙方式（`api/account/delete/route.ts` の deleteSteps）。FK cascade も張るが、列挙リストにも `chat_messages` / `chat_sessions` を追加する（二重防御。既存テーブルもこの方式）。

**パーソナライズ（表の価値）**
- スポット詳細を再訪したら直近セッションを復元（「続きから聞く」）。
- Phase 1 以降: 過去の質問傾向から次のサジェストチップを個人化。過去会話の本文をプロンプトへ注入するのは Phase 2 以降（トークン増と要約設計が要るため急がない）。

**分析（裏の価値、実体は需要シグナル）**
- 夜間バッチ（haiku-4-5 × Batch API 50%引）で当日の会話を分類し、**集計テーブル `chat_question_stats`** に落とす: 質問カテゴリ（同伴条件/設備/混雑/駐車場/**予約意図**/その他）× スポット × 回答可否（FACTS内で答えられたか）。
- 使い道: (a) 「答えられなかった質問」= DBに足りない事実 → 検証キューと fact_key 収集の優先度に直結 (b) 予約意図の件数 = Phase 4 店舗営業の資材 (c) 横断検索（Phase 2）へ進むかのゲート判定。
- 分類コスト: 上限3,000往復/日が全部発生しても haiku batch で**$0.2/日未満**。実利用では誤差。ストレージも実質ゼロ（テキスト行のみ）。
- **生ログの扱い**: 分析・エクスポートは分類済み集計テーブルに対して行い、生ログを分析基盤に出さない。生ログ保持は18ヶ月で cron 削除（期間は相談）。

**プライバシー・審査（確認済みの現状と必要な追記）**
- 現行プライバシーポリシー §3 は既に「本サービスの提供・品質及び体験の改善」「統計データの作成、分析（個人を識別できない形式に加工する場合を含みます）」を利用目的として明記済み（`src/app/privacy/page.tsx:152-163`）。**分析活用は既存の利用目的の枠内**。
- ただし取得情報の列挙（閲覧・いいね・訪問・検索等）に**「AIアシスタントとの相談内容」をデータ種別として追記**する。あわせて App Privacy ラベルの更新。チャットUI初回に「会話は品質改善のため保存されます」の1行を出す（同意の明示化とUX上の誠実さの両方）。
- ここまでやれば「表向きはパーソナライズ、裏は分析」という構図自体が消える。**両方とも表**であり、書いてあれば適法・書いてなければ APPI（利用目的の特定）と App 審査 5.1 系の両方を踏む。過去に Guideline 2.1（宣言だけの権限）で差し戻された実績があるアプリなので、審査面は特に先回りしておく。

## 5. 決定事項と残る相談ポイント

**決定済み（2026-08-30）**
1. 低確度バッジは出す。ただし**API先行・バッジUIは改善後または低確度＋情報提供導線が揃ってから**（§2.4 Phase 3）。低確度は**情報提供導線とセットでデザイン**する（§2.6）。
2. チャット会話は**サーバ保存**し、パーソナライズと分析の両方に使う（§3.7）。利用目的への「相談内容」追記とアプリ内の1行明示で両目的とも表に出す。
3. チャットの長期構想は**予約コンシェルジュ**（§3.6 Phase 4）。店舗側管理画面（別プロダクト）と連携し会話内で予約完結。MVPは SSE契約の拡張性・会話保存・予約意図の分類蓄積でこの終点に備える。
4. チャットは全画面常駐・全対応のグローバルアシスタント「ワンスポAI」1本（ヘッダー固定・FABポップなし・文脈はメッセージ単位）。無料枠は**数字非宣伝の実質無制限**（裏で20往復/日、§3.4）。
5. 回答は**カード＋一言説明のセット**を基本形にする（スポット/記事/イベント。LLMは present_*_cards ツールで構造化提示し、本文は比較の要点だけ）。DBで答えられないものは**Web検索で真摯に答え、未確認ラベルを必ず付ける**（§3.1）。

**残る相談ポイント**

5. 情報提供の構造化質問（§2.6-2）を tips シート改修のどの段階で入れるか（MVP同時か、バッジ表示後の追撃か）。
